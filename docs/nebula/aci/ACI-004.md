# ACI-004 — ADE Source → Draft → Approval → Publishing Queue
**Product:** Accretion Disk Engine (ADE)
**QEN:** Social Engine Build QEN
**Execution:** AIA / CAE — Local
**Type:** MVP Vertical Slice
**Implementation Changes:** AUTHORIZED
## Mission
Implement the first complete ADE-native operational workflow:
**Source → Draft → Review → Approval → Publishing Queue**
Use the existing **Next.js + SQLite** foundation.
Do not import Postiz or Mixpost code.
## 1. Source
Allow the Operator to create a real ADE source representing reusable TAIG activity.
Minimum fields should support:
* title;
* source content/description;
* source type;
* date;
* provenance/reference;
* notes where useful.
Persist sources in SQLite.
The Operator must be able to view existing sources and select one for content creation.
## 2. Draft
From a selected source, allow ADE to create a content draft.
The data relationship must preserve:
**Source → Draft**
The architecture should support AI generation, but this ACI must not become blocked by external AI credentials.
If live AI is unavailable, provide a clearly identified manual/mock generation boundary that still proves the workflow.
Drafts must remain editable.
## 3. Human Review
Implement a clear operator review experience.
The Operator must be able to:
* inspect the source;
* inspect the generated/created draft;
* edit the draft;
* approve it;
* reject it or return it to draft state.
Human approval is mandatory.
No unapproved content may enter the publish-ready queue.
## 4. Publishing Queue
Approved content may enter the Publishing Queue.
Minimum publishing states:
**PENDING | READY | PUBLISHED | FAILED**
Preserve useful social-plumbing patterns identified during ACI-003:
* never mark failed publishing as published;
* maintain explicit publishing state;
* retain failure information;
* prevent inappropriate duplicate execution;
* design the queue so real channel adapters can replace the MVP boundary later.
## 5. Facebook Adapter Boundary
Create a clean publishing-adapter interface.
Facebook is Channel 01.
For this ACI, implement a:
**Manual / Mock Facebook Adapter**
The system must clearly identify that this is not real Facebook publishing.
The adapter should prove the application can hand approved content to a channel-specific publishing boundary without coupling ADE's core workflow directly to Meta.
Do not require Meta credentials for ACI-004 completion.
## 6. UI Flow
The Operator should be able to move naturally through:
**Sources → Create → Review → Publishing**
Avoid making these feel like unrelated CRUD screens.
The UI should show where an item currently sits in the workflow and what decision is required next.
Preserve the ADE Hub design established during bootstrap.
## 7. Provenance
At every stage, ADE must retain enough relationship information to answer:
> What real source produced this content?
The relationship between source and resulting draft/publication must not be lost.
## 8. Truth Rules
Do not fabricate:
* clients;
* project outcomes;
* revenue;
* endorsements;
* capabilities;
* audience response;
* social metrics.
Mock/test data must be visibly identifiable as test data.
## 9. Validation Scenario
Use a clearly identified test source representing realistic TAIG activity.
Prove:
**Create Source**
→ **Create Draft**
→ **Edit Draft**
→ **Approve**
→ **Enter Publishing Queue**
→ **Manual/Mock Facebook Adapter**
→ **Published or controlled test-result state**
Also validate a failure path:
**Publishing attempt → failure → FAILED**
ADE must not incorrectly mark that item as published.
## 10. Required Evidence
CAE must return evidence that:
* sources persist;
* drafts persist;
* Source → Draft provenance survives;
* drafts can be edited;
* approval is mandatory;
* rejected/unapproved content cannot enter the publish-ready path;
* approved content enters the queue;
* publishing status is persisted;
* mock Facebook publishing is clearly identified;
* failure state behaves correctly;
* the workflow survives application restart.
