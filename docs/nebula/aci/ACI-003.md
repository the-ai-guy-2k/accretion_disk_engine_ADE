# ACI-003 — ADE Postiz + Mixpost Hybrid Harvest Assessment
**Product:** Accretion Disk Engine (ADE)
**QEN:** Social Engine Build QEN
**Execution:** AIA / CAE — Local
**Type:** Architecture / Reuse Assessment
**Implementation Changes:** LIMITED — assessment and small proof-of-concept work only
## Current Truth
ADE now has a localhost application foundation and Hub shell.
ADE is being built using the approved **hybrid strategy**:
**ADE-native product + ADE-native UI/workflow/intelligence + selective reuse/adaptation of proven open-source social infrastructure.**
Reference repositories:
**Postiz**
`https://github.com/gitroomhq/postiz-app`
**Mixpost**
`https://github.com/inovector/mixpost`
## Mission
Assess Postiz and Mixpost against ADE's required capabilities and determine exactly what ADE should:
**REUSE | ADAPT | LEARN FROM | BUILD ADE-NATIVE | DEFER**
The purpose is to avoid rebuilding solved social-management infrastructure while preventing ADE from becoming a reskinned Postiz or Mixpost.
## 1. Inspect Postiz
Assess relevant implementation patterns for:
* social account/channel integration;
* Facebook/Meta integration;
* post composer;
* media handling;
* scheduling;
* publishing queue;
* background jobs;
* publishing state/status;
* analytics;
* AI-assisted workflows;
* API architecture;
* authentication/configuration;
* reusable frontend concepts.
Identify specific modules/components/packages that may be useful to ADE.
## 2. Inspect Mixpost
Assess relevant implementation patterns for:
* self-hosted architecture;
* social account management;
* post composition;
* calendar/scheduling;
* queue/publishing workflow;
* media management;
* analytics;
* operator UX;
* API/provider abstraction;
* configuration;
* database/data-model patterns.
Identify specific patterns or components that may be useful to ADE.
## 3. Licensing / Dependency Review
Determine what may legally and practically be:
* directly reused;
* modified;
* adapted as a pattern;
* unsuitable for reuse.
Report relevant licensing obligations.
Do not copy code into ADE until its reuse status is understood.
## 4. Compare Against ADE
Evaluate both systems against these ADE areas:
* Sources
* Create
* Review / Approval
* Publishing
* Scheduling
* Channels
* Media
* Analytics
* Goals
* Audience Network
* Leads / Conversations
* Business Attribution
* Intelligence / Recommendations
* Hub UI
For every area classify the recommended ADE strategy as:
**REUSE CODE**
**ADAPT COMPONENT/PATTERN**
**BUILD ADE-NATIVE**
**DEFER**
Explain why.
## 5. Protect ADE Differentiation
The following should remain ADE-owned unless there is a compelling architectural reason otherwise:
* Goals → Decisions → Results workflow;
* ADE Hub experience;
* TAIG source intake;
* provenance;
* AI transformation tied to real business activity;
* mandatory human approval;
* Audience Network concept;
* content-to-business attribution;
* lead/opportunity relationship;
* ADE learning and recommendations.
Commodity social plumbing is the preferred area for reuse.
## 6. UI Assessment
Study Postiz and Mixpost UI/UX for useful ideas, but do not copy either interface wholesale.
Return recommendations for how ADE can make capabilities such as:
* Create
* Review
* Publishing
* Analytics
feel like parts of one ADE Hub rather than separate tools.
The governing UX remains:
**Goals → Decisions → Results**
## 7. Architecture Recommendation
Return a proposed hybrid architecture showing:
**ADE UI / Hub**
↓
**ADE Workflow + Intelligence Layer**
↓
**Reusable / Adapted Social Infrastructure**
↓
**Facebook / future channels**
Identify where the boundaries should exist.
## 8. No Broad Integration Yet
Do not perform full Postiz or Mixpost integration during ACI-003.
Small isolated proof-of-concept testing is authorized only when necessary to determine technical feasibility.
Do not:
* replace the ADE application;
* turn ADE into a fork;
* import large codebases blindly;
* rebuild the UI;
* implement the full publishing engine;
* add unrelated features.
